# 架构说明

[English](ARCHITECTURE.md) · [集成标准](INTEGRATION.zh-CN.md) · [项目总览](../README.zh-CN.md)

系统分三层，**层与层之间只守一条规矩**：模型可以决定**算什么**，但不能决定**什么是对的**。
正确性由两种语言各算一遍。

```
              用户任务书（地点 + 降雨情景 + 决策问题）
                          │
        ┌─────────────────▼──────────────────┐
        │  第三层：智能体（Agnes Harness）    │
        │  规划 → 调工具 → 读结果 → 验证 → 重试 │
        └─────────────────┬──────────────────┘
                          │  8 个工具，参数有 schema 校验，
                          │  写操作需人工审批
     ┌────────────────────┼────────────────────┐
     ▼                    ▼                    ▼
 flood_selftest      flood_run_event     flood_verify_report
 flood_resolve_place flood_fetch_dem     flood_publish_report
 flood_weather       flood_crosslang_check
     │                    │                    │
     └──────────┬─────────┴─────────┬──────────┘
                ▼                   ▼
   第一层 floodkit（Python）  第二层 verify-core.mjs（JavaScript）
   确定性水文计算             独立复算
```

## 第一层：确定性内核（`floodkit/`）

纯计算。没有模型、算术路径里没有网络、没有界面。跑
`python -m floodkit run …` 就能在**不需要 Agnes、不需要 API Key、不需要智能体**的情况下
复现报告里的每一个数字。

| 模块 | 职责 |
|---|---|
| `dem_source.py` | Copernicus GLO-30 瓦片的发现、下载与缓存 |
| `places.py` | 地名 → 研究区范围。只认南京，认不出就报错，不猜 |
| `weather.py` | 预报降雨，以三个独立模式的区间给出；15 天窗口 |
| `quality.py` | 输入质量门。`fatal` 级问题意味着**不产生栅格** |
| `terrain.py` | 优先级填洼、洼地单元划分、D8 汇流、水位—库容反演 |
| `landcover.py` | ESA WorldCover 10 m → 复合曲线数（TR-55，水文土壤组 C） |
| `hydro.py` | SCS-CN 产流、各洼地水位平衡、全域水量平衡 |
| `scenario.py` | 降雨情景定义 |
| `exposure.py` | OSM 承灾体分析：道路、建筑、下穿隧道、地铁口、学校、医院 |
| `runio.py` | **唯一的数据来源**：栅格、范围、OSM 缓存选择、深度分级定义 |
| `pipeline.py` | 端到端编排与报告组装 |
| `cli.py` | 命令行入口，每个子命令都向 stdout 输出 JSON |
| `samples.py` | 三类测试样例：正常 / 边界 / 失败 |

### 物理链条

```
DEM（GLO-30，30 m）
  → 投影到 UTM 50N 米制网格（EPSG:32650）
      地理坐标系下格子面积随纬度变化，不转米制则面积与流向都是错的
  → 质量门（坐标系、仿射参数、单位、量程、空洞、雨量、CN、研究区大小）
  → 优先级填洼            抹掉会截断汇流的噪声假坑
  → D8 汇流               每格流向 8 邻居中最低的一个
  → 洼地单元              低点 + 所有向它供水的格子
  → ESA WorldCover 10 m   → 复合曲线数 CN
  → SCS-CN 产流           P = Ia + F + Q
  → 水位—库容平衡         流入 = 蓄量 + 溢出 + 出流，逐洼地成立
  → 逐格水深              水位 − 地形
  → 五项验证              独立复算，不由出结果的同一段代码判定
  → OSM 承灾体            哪些有名字的路 / 楼 / 下穿 / 地铁口
```

南京旗舰运行实测形态：**341 × 321 格**，单格面积 **789.7 m²**（28.1 m 网格），
有效格 96,644，研究区 **76.32 km²**，筛后 **2,320** 个洼地单元
（5,877 个低于面积阈值的洼地仍被计入账目），100 mm 事件积水 **7.81 km²**。

## 第二层：独立验证器（`agh-plugin/verify-core.mjs`）

用 JavaScript 从零重写的同一套物理。它复算 SCS-CN **24 个算例**、
水位—库容反演 **10 个算例**（空洼地、恰好满库、超库容截断、平底并列高程、单格、零库容），
最差水位差 **8.9e-16 m**。

为什么是"换语言"而不是"再写一个函数"：

- **同一段代码跑两次什么也证明不了**，它只证明可重复，不证明正确。第二套实现必须独立地算出同一个答案。
- **它不是一次性的脚本。** 它跑在智能体自己的工具链里（`flood_crosslang_check`），
  所以每产出一个结果就当场复算，而不是某个更早日期跑过一次。
- **它抓出过 3 个真实分歧**，其中一个是只有"平底并列高程"这种边缘算例才会暴露的处理差异。

它的局限也写明：如果两套实现共享同一个**理解错误**，跨语言检查看不见。
这个缺口由解析校核覆盖——所以自检比对的是闭式解，而不是彼此。

## 第三层：智能体（`agh-plugin/index.mjs`）

在底座上注册 8 个工具。工具的元数据不是装饰，它决定了智能体的自主性能不能被审计。

| 工具 | 作用 | 副作用 |
|---|---|---|
| `flood_selftest` | 算之前先把内核验一遍 | 只读 |
| `flood_resolve_place` | 地名 → 研究区。只认南京，认不出就报错 | 只读 |
| `flood_weather` | 以三个独立模式的区间给出预报 | 联网 + 写缓存 |
| `flood_fetch_dem` | 拉取研究区 DEM 瓦片 | 联网 + 写缓存，需审批 |
| `flood_run_event` | 跑一次完整降雨事件 | 写产物，需审批 |
| `flood_publish_report` | 渲染交互式报告并在本机回环上提供访问 | 写派生页面 |
| `flood_verify_report` | 用 JavaScript 从报告里重新推导水量平衡 | 只读 |
| `flood_crosslang_check` | 用 JavaScript 重新推导解算器本身 | 只读 |

前两个工具的存在，是为了让智能体能质疑**输入**，而不只是质疑**输出**：
`flood_resolve_place` 阻止它凭空编一个研究区，`flood_weather` 让它发现
用户说的雨量和预报不符。**算得对不对从来不是弱点，前提对不对才是。**

## 验证挂在哪里

五项指标不是报告的附录——每一项都有归属、有阈值、有可以独立复算的位置。

| 指标 | 阈值 | 存放位置 | 谁可以复算 |
|---|---|---|---|
| D01 全域水量平衡 | ≤ 1 % | `report.json` → `water_balance` | `flood_verify_report`（JS） |
| D01b 栅格 vs 解算器 | ≤ 1e-6 | `report.json` → `water_balance` | 对交付的 GeoTIFF 重新积分 |
| D02 官方易涝点核对 | ≥ 70 % | `report.json` → `checkpoints` | 公布的易涝点清单 |
| D02b 排序检验（AUC + CI） | 报告用 | `report.json` → `checkpoint_ranking` | 对同一批点位重采样 |
| D03 跨语言复算 | ≤ 0.05 m | **智能体工具链，不在 JSON 里** | `flood_crosslang_check`（JS） |
| D04 参数敏感性 | 单调且 ≤ 45 % | `report.json` → `sensitivity` | 改动 CN 重跑 |

D03 **故意不写进** `report.json`：它在**每次运行的当时**于工具链里产生，
所以不会像一份存下来的结果那样放旧。

## 设计取舍与代价

| 取舍 | 理由 | 代价 |
|---|---|---|
| 静态蓄量平衡，而非水动力模型 | 水动力需要曼宁系数与管渠糙率，公开数据拿不到。未率定的参数会产出**看起来像验证过**的数字 | 没有流速、没有到达时间、没有河道顶托 |
| 不含排水管网 | 街道级管网不公开 | 结果**倾向于高估**：本会排走的水被当成积水 |
| UTM 50N 米制网格 | 地理坐标系下格子面积随纬度变化 | 该投影只在中国东部有效，不是全球通用 |
| 28.1 m 格网 | 由 GLO-30 重投影决定 | 路缘石、雨水口这个尺度表达不了 |
| `runio.py` 是唯一读取入口 | 深度分级、配色、范围、承灾体计数必须在地图、页面、GeoJSON、图表之间一致 | 新的消费方必须走它，不能自己解析文件 |
| 宁可拒绝也不猜 | 一个看起来合理的错答案比一次拒绝更糟 | 更粗糙的系统会答的请求，这里会失败 |

## 失败哲学

三条规则，每条都由代码而不是由文字保证：

1. **`fatal` 级质量问题意味着没有栅格。** 运行返回 `outcome: "rejected"` 和机器可读的原因，
   不会悄悄降级。
2. **未通过的指标就显示为未通过。** 渲染器逐字段断言页面与地图和 `report.json` 一致；
   一个把红色指标变绿的渲染器会直接拒绝生成输出。
3. **没验证过的范围就拒绝。** 空间只认南京，时间只到 15 天，两者都检查，两者都 fail-closed。

## 可复现性：是被测出来的，不是被声称的

- 把提交范围内的源码复制到一个干净目录，整条流水线可以重跑。
- 冷启动（无缓存）下载约 186 MB、耗时约 107 秒；缓存命中约 16 秒。两种情况数字相同。
- `python scripts/rebuild_outputs.py` 重建全部产物，然后跑完整验证链，包括智能体的执行记录。
- `tests/check_doc_consistency.py` 把文档里引用的数字与报告 JSON 对账，
  所以一份文档无法与它所描述的那次运行脱节。
