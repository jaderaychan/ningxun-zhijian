## 正文

### 先说结论

我们做了一个智能体：给它一场雨的雨量，它自己去拉地形数据、算产流、解淹没、
查 OpenStreetMap，最后给出**哪些下穿隧道和地铁口会进水**。

南京主城区、100 毫米降雨的结果是：

| 项 | 数值 |
|---|---|
| 淹没面积 | 7.81 km² |
| 被淹下穿隧道 | **117 / 420 段**（其中生命危险级 ≥0.3 m 的 **102 段**，车行隧道 **44 段**） |
| 被淹关键设施 | **146 / 292 个**，其中**地铁口 80 个** |
| 受影响道路 | 1722 / 4751 条 |
| 受影响建筑 | 1131 / 12080 栋 |
| 最危险的点位 | 南京五十中 2.55 m、**新街口地铁口 #2/#13 各 2.47 m**、张府园 #4 2.23 m |

新街口是南京最核心的商圈。看到"新街口地铁口 2.47 米"这个数字的时候，
我第一反应是"模型肯定哪儿错了"。

**但更值得说的是另一件事：我拿政府公布的易涝点清单去验，它不通过。**

---

### 一、为什么单列"下穿隧道"和"地铁口"

城市内涝最要命的不是路湿了。

**下穿隧道会从两端灌满，而且没有逃生路线。** 2021 年郑州京广路隧道就是这个场景。
**地铁口进水则直接连通地下空间**，水会顺着站厅往下走。

把它们混在"某条路积水 20 厘米"的清单里，等于把最要命的风险和最不要紧的风险一起报出去。
所以我们的报告里，这两类是**单独统计、单独排序**的。

有意思的是，OSM 数据里本来就带 `tunnel` 标签。研究区里能查到 **420 段**下穿通道和隧道，
全都是有名字的真实设施：九华山隧道、玄武湖隧道、通济门隧道、鼓楼地下立交……

---

### 二、我更想讲的是"我怎么知道它没算错"

一个能跑出数字的模型不难写。**难的是知道这个数字能不能信。**

我们的做法是：**五项指标全部由程序判定，不达标就在报告里失败，而不是由我们口头保证。**

| 指标 | 含义 | 实测 |
|---|---|---|
| D01 水量平衡 | 降雨 = 初损 + 下渗 + 蓄量 + 溢出 + 出流 + 残差 | **0.000000** |
| D01b 栅格 vs 解算器 | 从**输出的栅格文件**重算蓄量，对撞解算器内部的账 | **2.1e-16** |
| D03 跨语言复算 | 同一套物理用 **JavaScript 从零重写**，比对结果 | 水位差 **0.0 m** |
| D04 参数敏感性 | CN ±20% 时淹没面积必须单调且有界 | 单调，**30.0%** |
| 解析校核 | 填洼 / 水位—库容反演 / SCS 闭式解 | **5/5** |

D01b 是我最喜欢的一条：它拿**最终交付给用户的那个栅格文件**重新积分，去对撞解算器自己的账。
任何"算得对但写错了"的错误都会在这里暴露。

### 三、三个"已经不再测试任何东西"的测试

这部分是我最想分享的，因为它比模型本身更有普适性。

写测试的时候，我三次遇到**同一个陷阱**：测试还在"通过"，但它已经什么都不检查了。

**第一次：改了数据结构，负向对照失效了。**
我有一道测试是"故意改坏 Python 的答案，检查器必须报错"。后来我把 fixture 从单个
`basin` 改成 `basins` 数组，检查器跟着改了，**但这道测试还在改 `basin`**——
于是它改的东西已经没人读了，测试永远"通过"。

**第二次：故障注入注到了没人用的参数上。**
我有一个"CN 越界"的失败样例。后来支持了空间化 CN 栅格，那个样例改的还是**标量参数**，
而代码已经改用栅格了。于是这个"失败样例"**静默地跑成了一次正常分析**，还照样产出栅格。

**第三次：期望值是用被测函数自己算的。**
SCS-CN 的恒等式测试长这样：

```python
s  = potential_retention(cn)     # ← 被测函数
ia = initial_abstraction(cn)     # ← 被测函数
assert abs(p - ia - f - q) < 1e-9
```

**这是自证**：公式里少减一个常数，两边一起偏移，等式照样成立。

这三件事让我意识到：**"测试全过"根本不能证明任何东西。**

---

### 四、所以我去做了变异测试

做法很直接：**故意把源码改坏，看测试会不会抓。**

我注入了 15 种破坏——其中 6 种是这个项目历史上**真实出现过**的 bug：

| 注入的破坏 | 是否被抓到 |
|---|---|
| 保留公式里忘减 254（`S = 25400/CN`） | ❌ **第一次没抓到** |
| CN 不再钳制到 1..100 | ❌ **第一次没抓到** |
| 库容曲线改用填洼面高程（曾让库容≈0，蓄量差 570 倍） | ✅ |
| 把水铺到整个汇水区而非洼地面（曾造成 2.5% 水量不平衡） | ❌ **第一次没抓到** |
| 道路采样按"米"加密而函数要"像素"（曾让风险低估 3 倍） | ✅ |
| 曝光分析用正向变换代替逆变换（曾让所有 OSM 要素落到栅格外） | ✅ |
| 关掉高程包络检查 | ✅ |
| 只改文档字符串（对照组，**不应**被抓到） | ✅ 正确地没抓到 |

**第一次跑，有 3 个幸存者。** 三个都是"我修了 bug，但没有任何测试锁住它"——
意味着任何人一次编辑就能把 bug 改回来，而且不会有人发现。

补完测试后：**10/10 全部抓到，0 个幸存者。**

> 顺便说一个细节：有一条"忘减 254"的修复，我用的是**物理锚点**：
> `CN=100 ⇒ S=0`（不透水面没有滞留）。这是物理事实，
> **任何实现都伪造不了**——比"用被测函数算期望值"可靠得多。

### 五、然后是那个负结果

我做了一次外部验证。

数据来源是**江苏省公安厅交警总队 2015 年公布的南京市 32 处易积水路段**。
我把研究区从 76.3 km² 扩到 440 km² 去覆盖这份清单，用 OSM 道路名匹配定位到 27 处
（另 5 处是非道路要素，**报告为"未匹配"，不做猜测**）。

结果：

| 项 | 数值 |
|---|---|
| 二值命中率 | **11.1%**（3/27，阈值 70%） |
| 排序检验 AUC | **0.5193 ± 0.0573**（95% CI 0.407–0.632，含 0.5） |
| z 统计量 | **0.336**（判据 \|z\| ≥ 1.96） |
| 结论 | **与随机无法区分** |

**模型对这份官方清单没有任何预测能力。**

我当时的怀疑是"是不是我们点位定得不准"。所以做了对照实验：把"匹配到整条路的几何中心"
改成"求两条路的实际交点"（位置最多移动约 3.5 km），然后重跑：

| 定位方法 | 命中率 | AUC |
|---|---|---|
| 道路几何中心 | 7.4% | 0.4991 |
| **求实际交点** | **11.1%** | **0.5193** |

**没有翻盘。** 置信区间仍然横跨 0.5。

---

### 六、为什么失败，以及它换来了什么

原因不是模型算错了，而是**两者测的根本不是同一件事**：

> 那份清单是交警排查的"低洼易涝路段"，绝大多数是**管网能力不足、雨水口堵塞、
> 涵洞排水不畅**造成的。这些地方地形上根本不是洼地——雨停后水靠管网排走，
> 地形模型看不到它。

**AUC ≈ 0.5 恰恰是这一点的定量证据。**

而且，这个"预测不了"本身是有用的信息。于是我换了个问法：

> **对一个城市已经知道会积水的地点清单，模型能不能说清哪些是地形造成的、哪些不是？**

答案是可以。27 个官方点位分成三类：

| 判定 | 含义 | 数量 |
|---|---|---|
| `terrain_ponding` | 本场降雨模型就判它积水，**地形可以解释** | 6 |
| `terrain_storage_dry` | 确实坐落在一个真洼地里，只是这场雨没灌满 | 6 |
| `no_terrain_storage` | 这里**根本没有洼地** → **大概率是管网问题** | 15 |

**地形可解释合计 12/27 = 44.4%。**

这个区分的价值在于**它对措施有指向性**：

- `terrain_*` 类点位 → 响应的是**调蓄、下沉绿地、洼地改造**
- `no_terrain_storage` 类点位 → 响应的是**管道扩容、雨水口清理、涵洞改造**

**城市拿着这份分类，可以直接分工到不同部门。**

顺便发现一个值得注意的点位：**龙蟠路锁金北村路口，洼地容量 3.68 米**——
一个很深的地形洼地，只是 100 毫米情景还没灌满它。这类点位最值得用更大重现期复算。

---

### 七、一句话适用范围

我把这句话写在文档最显眼的位置：

> **本模型回答"地形上哪里会存水、存多深"，不回答"实际这场雨哪里会淹"。**
> 它适合做内涝风险普查与疑点筛查，**不能**作为防洪调度或预警的唯一依据。

一个不敢说自己边界的模型，等于在偷偷替用户做假设。

### 八、技术栈

- **Agnes Harness (AGH)** 作为智能体运行时，**8 个自定义工具**通过插件注册进去：
  `flood_selftest` / `flood_resolve_place` / `flood_weather` / `flood_fetch_dem` /
  `flood_run_event` / `flood_publish_report` / `flood_verify_report` / `flood_crosslang_check`
- **模型仅用 Agnes**（`agnes-3.0-flash`）
- 地形：Copernicus DEM GLO-30；下垫面：ESA WorldCover 10 m 复合曲线数
- 承灾体：OpenStreetMap（道路、建筑、下穿隧道、地铁口、学校、医院）
- 计算链路：DEM → 米制重投影 → 质量门 → 优先队列填洼 → D8 汇流 → 洼地单元 →
  复合 CN → SCS-CN 产流 → 水位—库容平衡 → 水深栅格 → 验证 → OSM 承灾体分析
