## 正文（从这里开始复制）

先说结论。

我们做了一个智能体：给它一场雨的雨量，它自己去拉地形数据、算产流、解淹没、查 OpenStreetMap，最后给出哪些下穿隧道和地铁口会进水。

南京主城区、100 毫米降雨的结果是：淹没面积 7.81 平方公里；被淹下穿隧道 117 段，其中生命危险级（水深 ≥0.3 米）102 段，车行隧道 44 段；被淹关键设施 146 个，其中地铁口 80 个；受影响道路 1722 条，建筑 1131 栋。

最危险的点位是：南京五十中 2.55 米、新街口地铁口 #2 和 #13 各 2.47 米、张府园 #4 2.23 米、南京定淮门长江隧道 1.62 米。

【插图1：四联故事图】
图注：一张图讲完链条——地形高程 → 复合曲线数（下垫面）→ 积水深度 → 风险点位。

新街口是南京最核心的商圈。看到"新街口地铁口 2.47 米"这个数字的时候，我第一反应是"模型肯定哪儿错了"。

但更值得说的是另一件事：我拿政府公布的易涝点清单去验，它不通过。

一、为什么单列"下穿隧道"和"地铁口"

城市内涝最要命的不是路湿了。

下穿隧道会从两端灌满，而且没有逃生路线。2021 年郑州京广路隧道就是这个场景。地铁口进水则直接连通地下空间，水会顺着站厅往下走。

把它们混在"某条路积水 20 厘米"的清单里，等于把最要命的风险和最不要紧的风险一起报出去。所以我们的报告里，这两类是单独统计、单独排序的。

有意思的是，OSM 数据里本来就带 tunnel 标签。研究区里能查到 420 段下穿通道和隧道，全都是有名字的真实设施：九华山隧道、玄武湖隧道、通济门隧道、鼓楼地下立交……

【插图2：关键点位风险图】
图注：红色为下穿隧道网络，圆点为关键设施（颜色越红水深越大）。右图放大到最深点位。

二、我更想讲的是"我怎么知道它没算错"

一个能跑出数字的模型不难写。难的是知道这个数字能不能信。

我们的做法是：五项指标全部由程序判定，不达标就在报告里失败，而不是由我们口头保证。

D01 水量平衡：降雨 = 初损 + 下渗 + 蓄量 + 溢出 + 出流 + 残差。实测 0.000000。

D01b 栅格 vs 解算器：从输出的栅格文件重算蓄量，对撞解算器内部的账。实测 2.1e-16。

D03 跨语言复算：同一套物理用 JavaScript 从零重写，比对结果。水位差 0.0 米。

D04 参数敏感性：CN 变化 ±20% 时淹没面积必须单调且有界。实测单调，30.0%。

解析校核：填洼、水位—库容反演、SCS 闭式解，与解析解逐位比对。5/5 通过。

D01b 是我最喜欢的一条：它拿最终交付给用户的那个栅格文件重新积分，去对撞解算器自己的账。任何"算得对但写错了"的错误都会在这里暴露。

三、三个"已经不再测试任何东西"的测试

这部分是我最想分享的，因为它比模型本身更有普适性。

写测试的时候，我三次遇到同一个陷阱：测试还在"通过"，但它已经什么都不检查了。

第一次：改了数据结构，负向对照失效了。我有一道测试是"故意改坏 Python 的答案，检查器必须报错"。后来我把测试数据从单个洼地改成一组洼地，检查器跟着改了，但这道测试还在改原来那个字段——于是它改的东西已经没人读了，测试永远"通过"。

第二次：故障注入注到了没人用的参数上。我有一个"曲线数越界"的失败样例。后来支持了空间化的曲线数栅格，那个样例改的还是标量参数，而代码已经改用栅格了。于是这个"失败样例"静默地跑成了一次正常分析，还照样产出栅格。

第三次：期望值是用被测函数自己算的。曲线数的恒等式测试长这样：先调用被测函数求出滞留量，再调用被测函数求出初损，然后断言三者之和等于降雨。这是自证——公式里少减一个常数，两边一起偏移，等式照样成立。

这三件事让我意识到："测试全过"根本不能证明任何东西。

四、所以我去做了变异测试

做法很直接：故意把源码改坏，看测试会不会抓。

我注入了 15 种破坏——其中 6 种是这个项目历史上真实出现过的 bug。

保留公式里忘减 254：第一次没抓到。

曲线数不再钳制到 1 到 100：第一次没抓到。

库容曲线改用填洼面高程（曾让库容约等于 0，蓄量差 570 倍）：抓到了。

把水铺到整个汇水区而非洼地面（曾造成 2.5% 水量不平衡）：第一次没抓到。

道路采样按"米"加密而函数要"像素"（曾让风险低估 3 倍）：抓到了。

曝光分析用正向变换代替逆变换（曾让所有 OSM 要素落到栅格外）：抓到了。

关掉高程包络检查：抓到了。

只改文档字符串（对照组，不应该被抓到）：正确地没抓到。

第一次跑，有 3 个幸存者。三个都是"我修了 bug，但没有任何测试锁住它"——意味着任何人一次编辑就能把 bug 改回来，而且不会有人发现。

补完测试后：10/10 全部抓到，0 个幸存者。

顺便说一个细节：有一条"忘减 254"的修复，我用的是物理锚点——曲线数等于 100 时滞留量为 0（不透水面没有滞留）。这是物理事实，任何实现都伪造不了，比"用被测函数算期望值"可靠得多。

五、然后是那个负结果

我做了一次外部验证。

数据来源是江苏省公安厅交警总队 2015 年公布的南京市 32 处易积水路段。我把研究区从 76.3 平方公里扩到 440 平方公里去覆盖这份清单，用 OSM 道路名匹配定位到 27 处（另 5 处是非道路要素，报告为"未匹配"，不做猜测）。

结果：二值命中率 11.1%（3/27，阈值 70%）；排序检验 AUC 0.5193，标准误 0.0573，95% 置信区间 0.407 到 0.632，包含 0.5；z 统计量 0.336，判据是绝对值不小于 1.96。

结论：与随机无法区分。

模型对这份官方清单没有任何预测能力。

我当时的怀疑是"是不是我们点位定得不准"。所以做了对照实验：把"匹配到整条路的几何中心"改成"求两条路的实际交点"（位置最多移动约 3.5 公里），然后重跑。

道路几何中心：命中率 7.4%，AUC 0.4991。

求实际交点：命中率 11.1%，AUC 0.5193。

没有翻盘。置信区间仍然横跨 0.5。

六、为什么失败，以及它换来了什么

原因不是模型算错了，而是两者测的根本不是同一件事。

那份清单是交警排查的"低洼易涝路段"，绝大多数是管网能力不足、雨水口堵塞、涵洞排水不畅造成的。这些地方地形上根本不是洼地——雨停后水靠管网排走，地形模型看不到它。

AUC 约等于 0.5 恰恰是这一点的定量证据。

而且，这个"预测不了"本身是有用的信息。于是我换了个问法：对一个城市已经知道会积水的地点清单，模型能不能说清哪些是地形造成的、哪些不是？

答案是可以。27 个官方点位分成三类：6 个本场降雨模型就判它积水，地形可以解释；6 个确实坐落在真洼地里，只是这场雨没灌满；15 个根本没有洼地，大概率是管网问题。

地形可解释合计 12/27，44.4%。

这个区分的价值在于它对措施有指向性：地形类的点位响应的是调蓄、下沉绿地、洼地改造；没有洼地的点位响应的是管道扩容、雨水口清理、涵洞改造。

城市拿着这份分类，可以直接分工到不同部门。

顺便发现一个值得注意的点位：龙蟠路锁金北村路口，洼地容量 3.68 米——一个很深的地形洼地，只是 100 毫米情景还没灌满它。这类点位最值得用更大重现期复算。

七、一句话适用范围

我把这句话写在文档最显眼的位置：

本模型回答"地形上哪里会存水、存多深"，不回答"实际这场雨哪里会淹"。

它适合做内涝风险普查与疑点筛查，不能作为防洪调度或预警的唯一依据。

一个不敢说自己边界的模型，等于在偷偷替用户做假设。

八、技术栈

Agnes Harness 作为智能体运行时，8 个自定义工具通过插件注册进去：flood_selftest、flood_resolve_place、flood_weather、flood_fetch_dem、flood_run_event、flood_publish_report、flood_verify_report、flood_crosslang_check。模型仅用 Agnes。

地形用 Copernicus DEM GLO-30；下垫面用 ESA WorldCover 10 米数据生成复合曲线数；承灾体用 OpenStreetMap（道路、建筑、下穿隧道、地铁口、学校、医院）。

计算链路是：DEM → 米制重投影 → 质量门 → 优先队列填洼 → D8 汇流 → 洼地单元 → 复合曲线数 → SCS-CN 产流 → 水位—库容平衡 → 水深栅格 → 验证 → OSM 承灾体分析。

写在最后

这个项目里我最满意的东西，不是"117 段下穿隧道被淹"这个结论，而是我知道这个结论在什么条件下不成立。

如果这篇文章只能留一句话，我希望是这句：

一个只报告通过的指标的团队，交出的报告是没有信息量的。

（正文结束）
